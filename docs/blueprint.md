\## 0. Decisions at a glance



| Area | Decision | Why |

| --- | --- | --- |

| App framework | \*\*Flutter\*\* (Dart) with \*\*Riverpod\*\* | One renderer gives consistent 60/120 fps UI and custom animation; mature BLE, MQTT and mDNS packages. React Native is viable if you already know React |

| Device chip | \*\*ESP32-C3 or ESP32-S3\*\* minimum | You need BLE for provisioning \*and\* ESP-WIFI-MESH. The ESP8266 has no BLE, so it would need a SoftAP fallback |

| Provisioning | \*\*BLE + QR\*\*, ESP-IDF unified provisioning with Security 2 (SRP6a) and a per-device proof of possession (PoP) | Same pattern as Tuya; encrypted from the first byte |

| Anti-hijack | One-time \*\*activation token\*\* from your cloud, plus PoP, plus per-home keys | A neighbour's phone or switch cannot be adopted |

| Local control | \*\*mDNS discovery + persistent WebSocket\*\* to the Root, app-layer AES-GCM | Push events, low latency, works with no internet |

| Cloud | \*\*MQTT over mutual TLS + device shadows\*\*. AWS IoT Core for the MVP; EMQX plus your own backend as the alternative | Shadows, jobs (OTA) and fleet provisioning come ready-made |

| Commands | \*\*Idempotent "set desired state" with a commandId\*\*, never "toggle" | Safe to retry over two paths without double-switching |

| Schedules and timers | \*\*Stored and executed on the device\*\* | They keep working when the internet or phone is gone |

| Mesh model | Root = \*\*gateway\*\*, other switches = \*\*sub-devices\*\* | Same model Tuya uses for Zigbee and BLE-mesh hubs |



Verify all package names and SDK behaviours below against their current documentation before committing. Library maintenance changes quickly.

\*\*Entity model\*\*



| Entity | Key fields | Notes |

| --- | --- | --- |

| User | userId, email or phone, devices of the phone | Auth via OIDC provider (Cognito, Firebase Auth, Auth0) |

| Home | homeId, name, timezone, \*\*homeKey\*\*, mesh ID, mesh AP password | Keys generated by the backend, stored encrypted |

\## 2. Device provisioning and onboarding



\### 2.1 Prerequisites on the device



\- \*\*Factory data\*\* (written once, in a protected partition): `deviceId`, a unique \*\*PoP secret\*\*, and a per-device cloud credential (X.509 certificate or key). The same `deviceId` and PoP are printed on the box/sticker as a \*\*QR code\*\*.

\- \*\*QR payload\*\* (example): `SW1:<productId>:<deviceId>:<PoP>`. The PoP is a secret, so the QR is a proof that you physically hold the product.

\- \*\*Provisioning state:\*\* only a \*\*factory-fresh or reset\*\* switch advertises the provisioning service over BLE. A switch that already belongs to a home does not advertise it.

\- \*\*Reset:\*\* long-press for 5 seconds (physical presence needed) wipes home data and re-enters provisioning mode.

\- The cloud keeps a \*\*registry\*\* of every manufactured `deviceId` and whether it is unclaimed or bound.



\### 2.2 End-to-end flow



1\. \*\*Sign in and pick a home.\*\* The user is authenticated. If they have no home, create one; the backend generates the home's mesh ID, mesh AP password and network key.

2\. \*\*Pre-permission screen.\*\* Explain why Bluetooth, camera, and (iOS) local network access are needed, then trigger the system prompts.

3\. \*\*Scan the QR.\*\* The app reads `deviceId` and PoP and checks the format. Manual entry is the fallback.

4\. \*\*Targeted BLE scan.\*\* Scan for the provisioning service UUID and connect \*\*only\*\* to the advertisement whose name or manufacturer data matches the `deviceId` from the QR. Neighbours' switches are ignored.

5\. \*\*Secure session.\*\* Establish an ESP-IDF protocomm session with \*\*Security 2 (SRP6a)\*\* using the PoP. If the PoP is wrong, the handshake fails and no data is exposed.

6\. \*\*Read device info.\*\* Firmware version, product ID, capabilities, and current state (should be "unprovisioned").

7\. \*\*Request an activation token\*\* from your backend for (user, home, deviceId). The token is single-use, bound to those three values, signed, and expires in about 10 minutes.

8\. \*\*Send the configuration\*\* over the encrypted session (see 2.4): Wi-Fi credentials, mesh configuration, home key (wrapped), cloud endpoint and the token.

9\. \*\*Device applies and reports progress\*\* over BLE notifications: `WIFI\_CONNECTING`, `WIFI\_OK`, `MESH\_JOINED (layer N)`, `CLOUD\_REACHED`, or an error code. If the device is the first node of the home, it will be elected Root and bring the cloud link up.

10\. \*\*Cloud activation.\*\* The Root publishes the device's activation message (signed with its per-device credential, carrying the token). The backend checks the token (valid, unused, unexpired, matches deviceId and home), checks the registry, then \*\*binds\*\* the device to the home and invalidates the token. Sub-nodes are activated \*through the Root\* as sub-devices.

11\. \*\*App confirms.\*\* The backend pushes a "device bound" event; the app closes the BLE link and shows the success screen.

12\. \*\*Name and room.\*\* User names the switch, assigns a room, and may immediately run a test toggle.



All nodes carry the router credentials, because ESP-WIFI-MESH needs them for root election and channel selection, even though only the Root actually uses them.



\### 2.3 Stopping neighbours from adopting each other's switches



| Control | What it blocks |

| --- | --- |

| QR carries the PoP | Someone without the product's sticker cannot open a session |

| SRP6a handshake with PoP | Eavesdroppers and wrong-PoP phones learn nothing |

| Targeted BLE connection by `deviceId` | Phone never talks to the wrong nearby switch |

| Already-provisioned devices do not advertise provisioning | A neighbour's installed switch cannot be re-adopted |

| One-time activation token bound to user, home and deviceId | A token cannot be replayed or reused for another device or home |

| Cloud registry (unclaimed or bound) | A bound device cannot be claimed by a second account; cloned IDs are detected |

| Per-home mesh ID, AP password and network key | A neighbour's switches can neither join your mesh nor forge commands |

| Physical reset required to release a device | Ownership transfer needs presence, then the cloud unbinds it |



\### 2.4 What the app sends, and what the ESP does



Wi-Fi credentials go through the standard provisioning config endpoint. Everything else goes through a \*\*custom endpoint\*\* (for example `sw-config`) registered on the device with the provisioning manager. Both travel inside the encrypted session.



```json

{

&#x20; "v": 1,

&#x20; "mesh": { "id": "<6 bytes>", "ap\_psk": "<random 16+ chars>", "max\_layer": 6 },

&#x20; "home": { "id": "h\_8f21", "net\_key\_wrapped": "<AES-GCM under the session key>", "key\_id": 1 },

&#x20; "activation": { "token": "<signed one-time token>", "cloud": "mqtts://iot.example.com:8883", "region": "ap-south-1" },

&#x20; "device": { "name": "Hall switch", "room\_id": "r\_hall" }

}

```



\*\*On the ESP, in this order:\*\* validate fields, store everything in encrypted NVS, set the router credentials, configure ESP-WIFI-MESH (ID, AP password, authmode WPA2, `nonmesh\_max\_connection = 0`), stop the provisioning service, start the mesh, then stream status over BLE until the first mesh event, and finally disconnect BLE.



| Failure | App message | Recovery |

| --- | --- | --- |

| Wrong PoP / handshake fails | "This code doesn't match the device" | Re-scan QR, check sticker |

| Wi-Fi auth failed | "Wi-Fi password rejected" | Re-enter password, device keeps provisioning mode |

| Router not found or 5 GHz only | "No 2.4 GHz network found" | Explain 2.4 GHz requirement |

| Mesh join timeout | "Device can't reach your other switches" | Move closer to an existing node, retry |

| Token rejected | "Setup expired" | Fetch a new token, resend config |

| Device already bound | "Already added to another home" | Owner must reset and remove it |

\### 3.2 Low-latency state (optimistic UI)



The toggle must \*\*feel instant\*\* regardless of the network.



1\. Tap writes `pending(desired = on, commandId)` into the device state \*\*in the same frame\*\*. The switch animates and a light haptic fires. This is the "<100 ms local feedback" and is independent of the network.

2\. The command goes out on the best path (3.3).

3\. An ACK or a state report with a matching `commandId` clears `pending` and confirms the state.

4\. On timeout the UI reverts to the last confirmed state, shows a small error, and marks the device as possibly offline.



Honest latency budget for the \*physical\* result on the local path:



| Step | Typical target |

| --- | --- |

| Tap to UI change | 16 ms (one frame) |

| Phone to Root over LAN (WebSocket) | 5 to 20 ms |

| Each mesh hop | 5 to 20 ms |

| Relay actuation | 10 to 20 ms |

| \*\*Total, local, 1 to 2 hops\*\* | \*\*roughly 50 to 120 ms\*\* (measure it; Wi-Fi power-save on the Root can add delay) |

| Cloud path | 150 to 500 ms plus network |



Tip: disable Wi-Fi power-save on the Root, and keep the WebSocket alive with a 5 to 10 s heartbeat.



\### 3.3 Dual-path routing



The app talks to the \*\*Root\*\*, never directly to sub-nodes, and the Root routes inside the mesh. The Root can change, so addressing is always by `deviceId` and `gatewayId`.



\*\*Do not decide "am I home?" from the Wi-Fi name.\*\* iOS restricts SSID access. Use \*reachability\*: the Root's mDNS record resolves, the WebSocket handshake succeeds, and a heartbeat arrived in the last 5 seconds.



```dart

Future<CmdResult> send(Device d, Command c) async {

&#x20; final id = newCommandId();                    // idempotency key

&#x20; state.markPending(d.id, c.desired, id);       // optimistic, same frame



&#x20; if (local.isReachable(d.gatewayId)) {

&#x20;   final ack = await local.send(d, c, id).timeout(800.ms, onTimeout: () => null);

&#x20;   if (ack != null) return state.confirm(d.id, id, ack);

&#x20; }

&#x20; if (cloud.isConnected) {                      // fall through, or race when local was slow

&#x20;   final ack = await cloud.send(d, c, id).timeout(4.s, onTimeout: () => null);

&#x20;   if (ack != null) return state.confirm(d.id, id, ack);

&#x20; }

&#x20; state.rollback(d.id, id);                     // nothing answered

&#x20; return CmdResult.unreachable;

}

```



Rules:



\- Commands are \*\*absolute\*\* (`set on`), carry a `commandId`, and the Root de-duplicates by it, so a command sent on both paths executes once.

\- Commands expire after about 30 seconds. Never replay stale switching commands later.

\- On a network change, re-probe immediately. When the Root changes (failover), mDNS announces the new address and the WebSocket reconnects with exponential backoff; the cloud path covers the gap.

\- iOS needs the Local Network permission and Bonjour service entries in `Info.plist`; Android needs a multicast lock and the Bluetooth and nearby-device permissions for the current API level.



\### 3.4 Local protocol choice



| Option | Pros | Cons | Verdict |

| --- | --- | --- | --- |

| WebSocket (+ app-layer AES-GCM) | Push events, one connection, simple in Flutter, `esp\_http\_server` supports it | Needs a TCP session per phone | \*\*Choose\*\* |

| CoAP over UDP | Light, fits constrained devices | Weaker Flutter tooling, you handle reliability and security | Optional later |

| HTTP polling | Easiest | No push, higher latency and battery cost | Debug only |



Local session security: the app and Root do a challenge-response handshake using a key derived from the home key (HKDF with per-connection nonces), then every message is AES-GCM with a counter. No cloud involved.



\### 3.5 Cloud: topics and shadow



```

home/{homeId}/dev/{deviceId}/cmd        app or backend -> device (via Root)

home/{homeId}/dev/{deviceId}/state      device -> everyone (reported state, retained)

home/{homeId}/gw/{gatewayId}/status     Root online, topology snapshot

home/{homeId}/events                    bound, removed, alarms

```



Broker ACLs: a device may publish only its own topics (the Root may publish for its sub-devices); an app may subscribe only to homes the user is a member of.



```json

{

&#x20; "state": {

&#x20;   "desired":  { "gang1": { "on": true }, "cmdId": "c-81f2" },

&#x20;   "reported": { "gang1": { "on": true }, "backlight": { "mode": "dim", "level": 30 },

&#x20;                 "online": true, "rssi": -58, "layer": 2, "parent": "n-02", "fw": "1.2.0", "ver": 412 }

&#x20; }

}

```



The Root also keeps a RAM copy of each sub-device's shadow so local control keeps working with the internet down.



\### 3.6 Multi-phone synchronisation



\- \*\*Every state change fans out\*\*: the Root pushes it to all connected local WebSocket clients \*and\* publishes it to the cloud; every phone subscribes to the home topics.

\- Each device keeps a monotonic `ver` counter. Apps ignore any report with `ver` lower than what they hold.

\- \*\*Conflict rule:\*\* last write wins by the device's accepted order (the Root serialises commands). Because commands are absolute, two phones tapping at once cannot leave the UI wrong; both converge on the reported state.

\- \*\*Reconnect:\*\* fetch a full snapshot (`GET /homes/{id}/devices`), then apply live deltas with `ver` greater than the snapshot's.

\- \*\*Offline indicator:\*\* a device is "offline" when the cloud says so (Root's last-will message or a missed heartbeat) \*and\* local probing fails.



\### 3.7 Schedules and timers



Schedules (time, repeat days, action) and countdowns live \*\*on the device\*\*. The Root distributes time (NTP) across the mesh and the timezone from the home settings. The app writes them and shows "synced to device" only after the device confirms. Limit the count (for example 20 per device) and show a clear error when full.

\## 5. Security, backend and roadmap



\*\*Backend services:\*\* auth (OIDC), home and device registry, token service, MQTT broker and shadow store, scheduler for OTA jobs, push notifications, audit log. Host in a nearby region (for example Mumbai) for latency and data-residency reasons.



\*\*Security baseline:\*\*



\- Short-lived access tokens, refresh token in secure storage, optional biometric app lock.

\- TLS with certificate pinning to your API. Device-to-cloud mutual TLS with per-device credentials, revocable.

\- Roles per home (owner, admin, member, guest) enforced on the \*\*server\*\* and in broker ACLs.

\- Signed and versioned OTA firmware with rollback protection.

\- App attestation (Play Integrity, App Attest) for sensitive endpoints, rate limits on token and login endpoints.

\- Privacy: minimise personal data, document retention, and plan for India's data protection law (DPDP Act) and store privacy declarations.

\## 7. Risks and open questions



| Risk | Mitigation |

| --- | --- |

| Android BLE differs across manufacturers | Test on 5 or more real phone models early; keep a retry-and-reconnect strategy |

| iOS local network permission denied | Fall back to cloud silently, and show a gentle prompt explaining the benefit |

| Root changes while the app is open | Always route by `gatewayId`; re-discover through mDNS; cloud covers the gap |

| Mesh is chatty or unstable in a real home | Run a soak test on the mesh before UI polish; consider Thread/Matter for the next hardware generation |
